tamias-bin — the declared bins lifecycle (proposal P-023): bins[] entries in a package manifest become commands on PATH.

Two declaration kinds (see tamias_core::BinDecl):

  • shim: "cli" + driver: <kind> — a generated front-end. Deploy writes a tiny shell script into the bin dir that execs tamias bin exec <label> <name> "$@"; tamias itself is the helper binary, so driver resolution stays dynamic (tamias-driver-<kind> on PATH/<tamias-home>/drivers/, with the capabilities fallback — e.g. a generic tamias-driver-cli). The script is preferred over a compiled helper: zero build, and the dispatch logic lives in one place (tamias bin exec).
  • payload: tools/bin/<triple>/<file> — a real binary shipped in the payload. Only the host triple’s file deploys; the <triple> segment in the declared path is substituted with [tamias_driver::target_triple] when the literal path doesn’t exist, so one manifest serves every platform. A payload whose tools/bin/ ships platform dirs but none for this host fails the install — the same rule drivers/bin/ already enforces.

Deployed payload bins link through the same per-package bin-alias/<@scope/>name → entry-dir alias tamias bin uses for bin/ payloads, so upgrades retarget once and every link keeps resolving. Ownership is proven by the link target (payload) or a # tamias-bin: <label> marker comment (shim scripts), which is what lets destroy/remove remove only what a package deployed — name collisions warn and last-deploy wins, never a hard error.

The bin dir itself is the caller’s ($TAMIAS_BIN_DIR → XDG_BIN_HOME → ~/.local/bin in the CLI); this crate takes explicit paths so every surface — CLI today, serve/TUI later — shares one implementation.
