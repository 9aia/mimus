tamias-driver-bupha — dual-surface driver for bupha’s CI state.

One binary, two consumers, disjoint argv:

pavo view driver (verbs take no --dir/--name):

  • manifest — print the [pavo_protocol::DriverManifest] JSON (discovery probe; never touches bupha state).
  • capabilities — merged JSON advertising BOTH surfaces: pavo’s {"capabilities": ["pavo"], "verbs": […"serve"…]} shape plus tamias’s "types": ["bupha"] and the provider verbs in verbs. pavo’s discovery greps capabilities/verbs for "pavo"/"serve"; tamias’s greps types for the content kind and warns on verbs missing from verbs — one payload satisfies both.
  • serve — ndjson JSON-RPC on stdio (see bupha_driver::serve). query:"ops" answers the engine ops manifest; query:"cli.<verb>" runs a bounded bupha CLI verb in a captured child.

Engine surface (P-021 — the bupha CLI as a generated surface):

  • ops — the ops manifest: every bounded bupha verb as a cli.<verb> wire query, derived from the engine’s own clap tree (bupha::command). Unbounded daemons (watch, agent, gha-runner) are surfaces, never ops.
  • run <argv> — engine passthrough: tamias-driver-bupha run doctor --json ≡ bupha doctor --json. Also the child side of cli.* wire queries (engine_ops::run_verb re-execs this same verb so engine output never touches the serve stream).
  • cli <argv> — the tamias bins[] shim verb (T-012): tamias bin exec runs <driver> cli --dir <payload> --name <pkg> <bupha argv> for a declared shim: cli bin. bupha’s engine IS the CLI, so this is a passthrough — strip the two standard driver flags and hand the rest to bupha::run_from with inherited stdio. That keeps full engine parity a generated ops→CLI surface can’t express: globals before the verb (--config), --help, the unbounded watch/agent/ gha-runner surfaces, and stdin-bound verbs all behave exactly like the retired bupha binary. There is no cli feature: cli is the shim verb, not a generated surface — the engine’s own argv grammar is the contract.

Optional surfaces: feature mcp embeds pavo-driver-kit’s surface layer — mcp serves the ops as MCP tools on stdio, equivalent to the standalone tamias-driver-mcp surface driver minus the PATH/discovery hop.

tamias content-type driver (type: bupha packages — tamias always passes --dir <payload> --name <pkg> [--config <f>], so these verbs are unreachable from pavo’s bare probes):

  • install — no-op (the operator config is deploy’s job; install only sees the evictable fetch-cache payload).
  • host — engine-host mode: run the watcher pipeline (bupha-watch) in-process against the deployed operator config — what provider units exec (tamias-driver-bupha host --config ~/.config/bupha/bundles/<name>.toml). Blocks until the sources stop; --dir/--name accepted per the tamias dispatch contract (--name supplies the default bundles/<name>.toml path when --config is absent). Standalone/dev mode (ADR-0007): the trigger listener this hosts is the fallback ingress — production webhook ingress is a peregrin campaign listener enqueuing ci-job via ci.enqueue.
  • worker — the ci-job consumption loop (P-002 §4.1): polls kind="ci-job" entities on a hypha/peregrin node ([worker] node / --node / BUPHA_WORKER_NODE, credential via [worker] node_token_env / --node-token-env / BUPHA_NODE_TOKEN), ci.claims pending jobs this box’s [worker] labels cover, runs them through the same bupha-watch pipeline, ci.completes the result. The second service a fleet deployment runs — worker boxes execute jobs the entity plane hands out.
  • deploy — merge the payload’s fleet.toml with tamias.yaml provider.ingress[] (tunnel.public_url, trigger.listen/kind) and write ~/.config/bupha/bundles/<name>.toml — the file the provider unit’s host verb consumes.
  • uninstall — remove that file.
  • hooks register|uninstall [--dry-run] [--api-base <url>] [--token-env <NAME>] — upsert/remove the GitHub webhooks provider.ingress[].hooks[] declare, via bupha_github’s REST path. Secrets resolve by NAME (env → cuora → keyring → ~/.config/bupha/env; cuora canonical per T-056); values are never printed. Standalone mode (ADR-0007): registers hooks at the bupha listener — production ingress is peregrin campaigns, so use this only for deployments with no peregrin.
  • health — JSON probe: webhook ping per ingress listen+path, else systemctl --user is-active per unit.
  • status — JSON per-unit is-active/is-enabled.
  • logs [--lines N] — journalctl --user over the provider units.
  • config-schema — JSON Schema (draft 2020-12) of the operator config deploy writes (tamias’s reserved verb).

See bupha_driver::ops for the implementation and bupha_driver::data for the pavo read plane.

engine_argv 🔒
cli verb argv (after the cli token) → engine argv (argv[0] included). tamias bin exec/driver exec prepend the standard driver flags — --dir <payload> --name <pkg> — which the engine doesn’t know; consume the leading run of those two (--flag v and --flag=v forms) and pass everything else through untouched. --config is deliberately NOT stripped: it’s a bupha global, so a user-passed one must reach the engine’s own parse.
