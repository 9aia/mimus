tamias-serve — the ndjson JSON-RPC surface for embedding: read one JSON request per line on stdin, write one JSON response per line on stdout. Same wire as sepia serve / cuora serve / myco serve.

Ops: install, plan, sync, list, info, verify, remove, search, publish, registry.list, registry.get, registry.add, registry.remove. Requests are {"op":"…", …}; responses are {"ok":true,"result":…} or {"ok":false,"error":"…"}.

plan is tamias install --plan — {"op":"plan","ref":…, "allow_drivers":…} fetches/plans and reports what a real install would do (includes, drivers, provider services, trust tier, would-be problems) without committing or dispatching.

sync reconciles the server’s cwd project dep set against the store + tamias.lock — the same tamias sync semantics ({"op":"sync","locked":…,"from_lock":…,"allow_drivers":…, "dir":…}; dir defaults to .). from_lock: true treats tamias.lock itself as the spec (no manifest consult, no lock rewrite). Per-dep outcomes come back in result.deps; a bundled-driver consent refusal is an ok:false error like install’s.

search/publish/registry.* resolve named registry sources and config writes through tamias-registry-open — the same code the tamias CLI verbs use, so the wire surface can’t diverge.

Trust boundary. Stdin is fully trusted: install accepts allow_drivers:true (bundled-driver consent), and publish/registry.add/registry.remove mutate config and the registry. Embedders must treat the pipe as a privileged channel — never expose it to untrusted input.
