tamias-driver — the content driver host: discovery + dispatch of tamias-driver-<type> executables, with no product knowledge in tamias.

A driver is an executable tamias-driver-<type> on PATH or in <tamias-home>/drivers/. tamias reads a package’s type:, resolves its driver, and runs:

tamias-driver-<type> <verb> --dir <dir> --name <name> [--config <file>]

verb ∈ {install, deploy, uninstall} for the lifecycle dispatch; drivers may declare further provider verbs (health, hooks, …) in capabilities.verbs, reached through dispatch_with_args — tamias driver exec. A driver may also answer capabilities.

config-schema — a reserved verb by convention. A driver that consumes a --config file may implement config-schema: dispatch it and the driver prints a JSON Schema (draft 2020-12) on stdout describing that file’s format, exit 0. Drivers without one exit non-zero with a clear stderr message — callers treat that as “unsupported” and surface it, never a crash. The standard --dir/--name/--config flags are appended like any verb, but the schema should be instance-agnostic. Fetch it with config_schema or tamias driver config-schema <pkg>.

Validating a config against the schema is deliberately driver-side, not engine-side: tamias ships no JSON Schema validator, so a driver that wants validation implements it as an ordinary provider verb — tamias driver exec <pkg> config validate --config <file> is the intended shape.

Operator config overrides (T-026). Drivers that generate config on deploy/install wipe hand edits every run. tamias owns the persistence half in overrides: drop-in fragments under <config>/tamias/deploy.d/<kind>/<name>/ (tamias deploy --set key=value edits the cli.yaml fragment), injected into every dispatch as overrides::OVERRIDES_ENV. A driver that generates config merges the dir’s fragments over the generated doc before writing — tamias_core::merge_values gives the same deep-merge include: overlays use. Installing a product drops its driver into <tamias-home>/drivers/ (from the payload’s drivers/ dir), so tamias finds it. The engine never links a product crate.

Bundled drivers. A payload’s drivers/ dir ships ready-to-run driver files:

  • drivers/<name> — portable drivers (interpreted scripts like #!/usr/bin/env python3 ship as source).
  • drivers/bin/<target-triple>/<name> — compiled drivers, one dir per rustc target triple (x86_64-unknown-linux-gnu, …). At install time only the dir matching target_triple is copied; a package that ships platform dirs but none for this host fails the install with a clear error rather than silently dropping the driver.

Both forms land flat in <tamias-home>/drivers/ (executable bit set), stay inside the payload digest, and are consent-gated — see drivers_allowed.

Functions§

bundled_drivers
Names of the driver files a payload ships under drivers/ — regular files only, mirroring register_bundled_drivers’s filter, plus the platform bins under drivers/bin/<triple>/ (reported as bin/<triple>/<name>). Lets callers detect (and gate) bundled drivers before copying or dispatching them — including binaries for other platforms, which are still bundled executable content.
capabilities
Run a driver’s capabilities probe and return the JSON it prints — the same bounded call [driver_handles] makes, exposed for the tamias drivers listing. Ok only on a zero exit and parseable JSON; anything else is an Error the caller renders as “unreachable”.
config_schema
Fetch a kind driver’s config-schema — the reserved verb that prints a JSON Schema (draft 2020-12) describing the --config file the driver consumes. Bounded like capabilities (a probe, not a lifecycle verb). Ok(None) = no driver found; a driver that doesn’t implement the verb exits non-zero and surfaces as Error with its stderr — “unsupported” is a normal outcome, not a crash.
discovered_drivers
Every discovered driver as (type, path) — for doctor and tamias drivers.
dispatch
Dispatch a verb to the content type’s driver. Returns whether a driver ran (false = nothing to do — a files package, or no driver present).
dispatch_with_args
dispatch plus arbitrary trailing argv — the tamias driver exec passthrough for provider verbs beyond the lifecycle three (hooks register, health, …). args land after the standard --dir/--name/--config flags. On success the driver’s captured stdout/stderr come back for the caller to render — provider verbs answer with status JSON the operator needs to see. Ok(None) = no driver found (same false as dispatch).
drivers_allowed
Consent for registering + running payload-shipped drivers: the caller’s --allow-drivers flag, or TAMIAS_ALLOW_DRIVERS=1 in the environment.
drivers_dir
The <tamias-home>/drivers dir.
find_driver
Find the driver for a content type — tamias-driver-<kind> on PATH, then <tamias-home>/drivers/. Kinds outside the manifest charset (tamias_core::is_valid_kind) never resolve — a hand-built store record can’t smuggle ../ into the driver-name join.
register_bundled_drivers
Copy any bundled drivers a payload ships into <tamias-home>/drivers/ so tamias discovers them: top-level drivers/<name> files as-is, plus the drivers/bin/<target-triple>/ dir matching this host (see target_triple). Platform bins for other triples are skipped; a payload that ships platform dirs but none for this host is an error — the package intended a runnable compiled driver and can’t provide one. Returns action lines.
tamias_home
<tamias-home> — $TAMIAS_HOME → $XDG_DATA_HOME/tamias → ~/.local/share/tamias → ./.tamias.
target_triple
The rustc target triple this build was compiled for (x86_64-unknown-linux-gnu) — captured at compile time by build.rs (cargo:rustc-env), so it always names a real cargo target even where std::env::consts can’t reconstruct the vendor/os/env spelling.
