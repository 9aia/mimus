Operator deploy-override drop-ins — see the module docs and the crate-level contract note. Deploy overrides — the durable operator-config persistence channel (T-026).

Kind drivers regenerate operator config on every deploy/install (e.g. ~/.config/peregrin/serve/<name>.yaml), wiping hand-applied edits. tamias owns the storage side of the fix; the driver owns the merge (it alone knows the generated document’s shape):

  • Drop-in dir per installed package: <config>/tamias/deploy.d/<kind>/<name>/ — <config> is $XDG_CONFIG_HOME/tamias (~/.config/tamias fallback), or $TAMIAS_DEPLOY_D when set. Every *.yaml/*.yml/*.json file in it is a partial document, merged in sorted-filename order — later files win — with tamias_core::merge_values semantics (the same deep-merge include: overlays use: dicts per-key, arrays concat high-first with id dedupe).
  • tamias deploy <pkg> --set key=value (repeatable) edits the cli.yaml fragment inside that dir — dotted keys build nested maps (a.b.c=v), values parse as YAML (--set 'nodes=[1,2]', --set 'x={k: v}'); --unset key removes a path, --clear-overrides drops the package’s whole dir. Because cli.yaml is just one fragment, hand-written files sorting after it (zz-*.yaml) still win over --set values.
  • At dispatch time dispatch hands the driver the drop-in dir via [OVERRIDES_ENV] whenever it exists — every lifecycle verb (install/deploy/uninstall) and driver exec passthrough, so CLI, tamias serve, sync, and the TUI all carry it. Drivers that generate config merge the fragments over the generated doc before writing; drivers that don’t simply ignore the variable.

The <kind>/<name> key is exactly what the driver sees on argv (--name is the bare record name — scope isn’t part of it), so two scopes sharing a name+kind share overrides; that’s inherent to the driver contract, not this channel.

Constants§

OVERRIDES_ENV
Env var naming the package’s deploy-override drop-in dir, injected into every dispatched driver whose dir exists. Drivers merge its fragments over generated config — see the module docs.
OVERRIDES_ROOT_ENV
Env var naming the overrides root (the deploy.d dir itself) — an escape hatch for tests and nonstandard config homes; overrides $XDG_CONFIG_HOME/$HOME discovery when set.

Functions§

clear_overrides
Drop the package’s whole drop-in dir — every fragment, cli.yaml included. Ok(true) when a dir was removed.
merged_overrides
Fold every fragment in dir into one document — sorted by filename, later files higher priority, tamias_core::merge_values per file (deep-merge: dicts per-key, arrays concat high-first with id dedupe). Ok(None) when the dir is absent or holds no fragments; a malformed fragment is an error, never silently skipped.
overrides_root
The overrides root — $TAMIAS_DEPLOY_D, else $XDG_CONFIG_HOME/tamias/deploy.d, else ~/.config/tamias/deploy.d. None when no home/config dir resolves (same posture as tamias-registry-open’s user_config_dir).
package_dir
The drop-in dir for one (kind, name) under root — None when either component fails its charset (a hand-built store record can’t smuggle ../ into the join; dispatch then simply injects nothing).
package_overrides
The merged persisted overrides for one package — what --show prints. Ok(None) when nothing is persisted.
parse_set_arg
Parse one --set argument — key=value where key is a dotted path (a.b.c) and value parses as YAML (plain scalars, lists, inline maps all work; unparseable values stay literal strings).
set_override
Set key (dotted path) to value inside doc, creating intermediate maps (or arrays when the next segment is numeric). Returns the fragment path written.
unset_override
Remove key (dotted path) from the package’s cli.yaml fragment. Ok(true) when something was removed; the file is deleted when it empties out.
