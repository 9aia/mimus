tamias-install — the one install pipeline, shared by tamias install/add/update (the CLI) and the install op of tamias serve (the JSON-RPC surface):

ref → parse → plan → fetch-cache hit or fetch+commit
    → payload manifest → bundled-driver consent gate
    → `template.extends` parent materialization (`.scarab-parent/`)
    → register bundled drivers → driver `install` dispatch
    → store commit → declared `bins[]` deploy

Driver work runs before the store commit: a missing or failing driver fails the install with no committed entry (the fetch-cache entry is content-addressed and stays). Bundled drivers/ are arbitrary code shipped inside the package — they are never registered or executed without explicit consent (--allow-drivers, "allow_drivers":true, TAMIAS_ALLOW_DRIVERS=1, or a recorded per-package consent — see [consent]).

The bins[] deploy is the mirror image — after the commit, on every install path (CLI, serve op, sync dep, TUI job), via install_with_progress_opts’s deploy_bins tail; a deploy failure fails the install post-commit (tamias bin deploy --force is the retry).

Progress is reported through Progress events so each surface keeps its own rendering: the CLI prints tamias: lines to stderr and driver actions to stdout; tamias serve drops them. Consent hints embedded in errors are surface-tuned via Surface.

sync_project (the sync module) reuses the same pipeline to reconcile a project manifest’s deps: against the store + tamias.lock — install-if-missing-or-drifted per dep, never removes.

Functions§

install
Install reference silently — no progress events, Surface::Rpc consent hints. The tamias serve install op’s shape.
install_with_progress
Install reference, reporting Progress events to report.
install_with_progress_opts
install_with_progress plus the post-commit bins[] deploy toggle — deploy_bins: false is the CLI’s --no-bins: the entry commits but declared bins stay undeployed (tamias bin deploy materializes them later). Every other caller deploys: the deploy lives here, in the one pipeline, so tamias install/add/ update, tamias serve’s install op, sync deps, and the TUI’s install jobs all land declared bins on PATH uniformly. Only the top-level entry deploys — include:/extends bases recurse through [install_inner] directly and never reach this tail.
is_driver_consent_refusal
Whether err is the bundled-driver consent refusal — the one failure an interactive surface can recover from by re-running with consent (tamias ui’s modal). Matches the marker the pipeline embeds; the Surface only changes the trailing hint.
plan_install
tamias install --plan — the dry-run half of [install_inner]: parse → plan → fetch-or-cache → manifest, then report instead of act. include: entries are classified ([include::plan_include]), never resolved — no recursive installs, no overlay, no composed digest. Driver work stops at resolution ([tamias_driver::find_driver] may capabilities-probe discovered drivers — trusted local binaries, 10s timeout); bundled-driver registration, dispatch, and the store commit never run.
remove
remove — the lightweight uninstall shared by tamias serve’s remove op and tamias ui’s Remove job: find the entry, dispatch the kind driver’s uninstall verb before dropping the store entry (a failing driver keeps it), then Store::remove. A missing driver on a non-files kind reports through warn — provider resources may remain. (files is built in; tamias uninstall / tamias-provider::uninstall is the provider-aware teardown, and the CLI’s bare remove skips dispatch entirely.)
sync_project
Sync the project in dir against the store under env.store_root and dir/tamias.lock. SyncOptions::source picks the spec: SyncSource::Deps (default) reconciles the project manifest’s deps: (the manifest is required and the lock is refreshed per install); SyncSource::Lock treats tamias.lock itself as the spec — no manifest is consulted and the lock is never rewritten. Progress streams through report exactly like install_with_progress; surface tunes consent hints.
