bupha-gha-runner — bupha as a GitHub Actions self-hosted runner: the runner registers with GitHub, polls the message queue, executes the jobs it is offered, and reports results — enough of the actions/runner broker protocol that a workflow can say runs-on: [self-hosted, bupha] and GitHub schedules onto it.

This is the opposite direction from bupha-gha: that crate reads .github/workflows/*.yml and executes them as bupha CI; this crate makes bupha a runner GitHub itself drives. The name was reserved for this by T-054 — gha stays the workflow dialect, gha-runner is the broker protocol.

§Protocol coverage

Implemented (the flow actions/runner’s run.sh performs):

  • registration — POST {api}/actions/runner-registration trades a short-lived registration token (or a PAT-minted one via POST /repos/{repo}/actions/runners/registration-token) for the Actions service URL + bearer token; Default pool lookup; POST …/pools/{pool}/agents with an RSA public key.
  • session — POST/DELETE …/pools/{pool}/sessions; RSA-OAEP session-key unwrap and AES-256-CBC message decryption when the session carries a key.
  • queue — long-poll GET …/pools/{pool}/messages, ack via DELETE …/messages/{id}; broker migration (BrokerMigration → POST /session, GET /message on the broker) and job offers (RunnerJobRequest → POST {run_service}/acquirejob).
  • execution — script steps via the job’s shell, actions/checkout via git, $GITHUB_ENV/$GITHUB_OUTPUT/$GITHUB_PATH env files, success()/failure()/cancelled()/always() conditions, job lease renewal, cancellation messages.
  • results — WorkflowStepsUpdate, signed-URL log upload (append-blob + metadata), completejob with the outcome and the evaluated job outputs: map (the jobOutputs templates the service sends are resolved against collected $GITHUB_OUTPUT values for steps.*/needs.*/env.*/ github.* refs — the channel needs.*.outputs reads back).

Explicitly out of scope (fail loudly, never silently): node/docker actions other than actions/checkout, container jobs, service containers, ${{ }} expression evaluation inside step fields (the service pre-compiles them — expressions that survive to the runner are passed through literally), the realtime log feed (websocket), and artifact/cache/upload endpoints.

Modules§

agent
The listener: connect, open a session, long-poll the queue, run each job offered, report the outcome, acknowledge the message.
client
The HTTP client: one method per call the runner makes, in the order a runner makes them. Blocking ureq, no async.
crypto
The cryptography the protocol needs: an RSA keypair per runner (public half registered, private half signs the token assertion and unwraps session keys), JWT bearer assertions, RSA-OAEP session key unwrap, and AES-256-CBC message decryption.
encoding
The two JSON wrappings the Actions service puts around job data.
exec
Job execution: expanded JobMessage steps → spawned shell children in a per-job workspace. Script steps run through bash/sh, actions/checkout clones the repository, and the $GITHUB_* file commands (GITHUB_ENV/GITHUB_OUTPUT/GITHUB_PATH) the protocol requires are implemented per job.
register
Registration: turn a short-lived registration token (or a PAT that mints one) into credentials that last — the equivalent of what config.sh writes to .runner.
report
Reporting: step states to the results service as they happen, logs at the end, and the job’s conclusion to the run service. Everything here is best-effort — a results-service hiccup must not kill a job that already ran; failures are logged to stderr.
types
Wire types for the Actions runner protocol — the shapes the broker, the run service and the results service exchange.
