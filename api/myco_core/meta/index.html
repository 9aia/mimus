meta.toml model + the pure id-allocation logic.

Counters are persistent — done tasks leave TODO.md and ids must never be reused, so TODO.md alone can’t tell you the next T-NNN. Registry computes next ids from counters plus a set of observed ids (reconcile = counter ≥ max-seen + 1), which is what the store uses to recover from hand-edits.

Structs§

NextCounters
Per-kind next-counters — meta.toml’s [next] table. Missing keys default to 1 so a partial [next] survives a hand-edit. Builtin kinds keep their fixed keys (t, i, …); user kinds (P-008) land in extra keyed by lowercase prefix (s = 4). Unknown keys ride extra too — the kind table, not serde, decides whether a key names a real kind (a typo’d counter can’t reissue ids anyway: observe floors every counter above the ids on disk).
ProjectMeta
meta.toml — the one piece of project state that isn’t derivable from the item files. Unknown keys are rejected: a typo’d table ([netx]) would otherwise silently drop the real counters and restart id allocation at 1 — done ids get reissued, colliding with their handoffs and history.
Registry
Id allocator — pure. Seed from ProjectMeta::registry, observe_all every known id, then alloc; take the bumped counters back out via counters to persist.
