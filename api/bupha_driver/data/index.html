data — the read plane: bupha’s on-disk state.

bupha has no serve wire, so the driver reads the same files the watcher writes, under worktree.base:

surfacefile / probewritten by
run history<base>/history.jsonlbupha-history — one JSONL record per finished run ({sha, repo, status, wall_secs})
queue state<base>/queue.jsonbupha-queue JsonQueueStore — repo key → PersistedQueue {pending, running}; tmp+rename writes mean a direct read never sees a torn file
watcher unitssystemctl --user is-enabled/is-activebupha-systemd (bupha service status)

The bupha CLI is not the data plane: runs/log/explain print human-formatted text with no --json, so proxying them would mean parsing prose. Reading the files directly — through the same crates that write them — is the stable read path.

Which base: first hit wins —

  1. Request params — base (a worktree.base path) or config (a bupha.toml/bupha.yaml path, like the CLI’s --config).
  2. Config discovery via [FileSource]: $BUPHA_CONFIG, then ./bupha.{yaml,yml,toml}, then ~/.config/bupha/bupha.* — the watcher’s own resolution order.
  3. The compiled default /tmp/bupha (default_wt_base).

Queue kind comes from the same config ([queue] kind); only the dev json store is readable here — anything else degrades the queue view to a note.

queue_entries
Queue entries from <base>/queue.json via the same [JsonQueueStore] the watcher persists through. The store’s tmp+rename writes mean a direct read never sees a torn file, so no snapshot copy is needed (the old redb impl required one — the watcher held the database lock for its whole lifetime).
queue_path
<base>/queue.json — the dev queue store (kind = “json”).
repo_matches
bupha runs <repo> semantics: a bare repo filter also matches its job keys — runs o/r catches o/r:gate; runs o/r:gate stays exact.
resolve
Resolve the read plane for one request’s params. Cheap enough to run per query — config load is one small file read.
run_records
History records filtered by repo and capped to the LAST limit entries (the file is append-only, so the tail is the freshest).
unit_status
systemctl --user is-enabled/is-active for one unit — the same probe bupha service status runs (via bupha-systemd). The probe itself reports “unknown” on spawn failure; a hard io error degrades to a message string rather than failing the view.
unit_statuses
