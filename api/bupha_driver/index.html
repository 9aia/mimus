bupha-driver — library half of tamias-driver-bupha, the pavo view driver for bupha’s CI state.

Verbs (the tamias driver contract, served by src/main.rs):

  • manifest — print the [pavo_protocol::DriverManifest] JSON.
  • capabilities — {"capabilities": ["pavo"], "verbs": […]}.
  • serve — ndjson JSON-RPC on stdio: {"op":"manifest"}, {"op":"views"}, {"op":"view","view":…,"params":{…}}, {"op":"query","query":…,"params":{…}} → {"ok":true,"result":…} / {"ok":false,"error":…}. The loop itself is pavo_driver_kit::serve_stdio; render/submit/ jobs/notifications answer ok:false — this driver claims none of them.

Engine ops (the “CLI-as-generated-surface” contract, P-021): {"op":"query","query":"ops"} answers the ops manifest — every bounded bupha CLI verb derived from the engine’s own clap tree (engine_ops); query:"cli.<verb>" re-execs tamias-driver-bupha run <argv> in a captured child and returns {op, argv, code, stdout, stderr}. Unbounded daemons (watch/agent/gha-runner) ride surfaces.

Read path: bupha keeps no serve wire — its state is files under worktree.base (history.jsonl, queue.json, plus the systemd user units the watcher manages). The driver reads those directly through the same crates the watcher uses (bupha-config-file for config resolution, bupha-queue for the queue store, bupha-systemd for unit state) — the most stable read path available; the bupha CLI’s runs/log verbs print human text with no --json, so proxying them would mean parsing prose. See data.rs.

One JSON answers both: the kit’s {capabilities, verbs} shape plus "types": ["bupha"] and the tamias provider verbs folded into verbs.

serve
The serve verb — ndjson JSON-RPC on stdio until EOF or a broken pipe, via pavo-driver-kit’s loop (same semantics as the hand-rolled loop this replaces: blank lines skip, parse failures answer ok:false, a dead client exits quietly).
